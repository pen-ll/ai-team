# UI 常见体验优化规则

## 触发

当需求涉及用户交互、网络请求、数据展示时加载。

---

## 一、防抖与节流
看当前项目是否有防抖/节流的通用实现，若没有则按以下规则实现。

### 防抖（Debounce）

**适用场景**：搜索框输入、窗口 resize、表单校验等"等用户操作完再执行"的场景。

**规则**：用户连续触发事件时，只在最后一次触发后延迟执行。

```
默认延迟：350ms
若用户明确要求或场景特殊（如实时搜索建议），可调整为 150-500ms
```

### 节流（Throttle）

**适用场景**：滚动加载、按钮连续点击防护等"固定频率执行"的场景。

**规则**：固定时间间隔内只执行一次。

```
默认间隔：350ms
若用户明确要求或场景特殊，可调整为 100-500ms
```

### 实现方式

按平台语言实现，不限定具体写法。关键原则：
- 防抖：每次调用重置计时器
- 节流：记录上次执行时间，间隔不足则跳过
- 组件销毁时必须清理计时器，避免内存泄漏

## 二、界面状态管理

### 核心原则

任何涉及**网络请求**或**异步数据加载**的页面/组件，必须覆盖以下 4 种状态：

```
Loading  →  加载中，展示加载指示器
  ↓
  ├─ 成功 → Content（正常展示数据）
  ├─ 空数据 → Empty（展示空状态提示）
  └─ 失败   → Error（展示错误信息 + 重试入口）
```

### Loading 状态

- 首次加载时展示 loading 指示器（骨架屏/Spinner/进度条）
- 加载指示器应居中展示
- 若数据已在加载中，禁止用户重复触发加载操作（如按钮置灰）

### Empty 状态

- 数据为空时展示友好的空状态提示（非白屏）
- 包含：空状态图标/插图 + 提示文案 +（可选）操作按钮
- 提示文案应说明"为什么为空"而非仅显示"暂无数据"

### Error 状态

- 网络请求失败时展示错误提示
- 包含：错误信息文本 + **重试按钮**（必须）
- 错误信息应包含具体原因（如"网络连接失败，请检查网络后重试"），而非仅"加载失败"
- AI 可自行决定错误信息的展示方式（Toast / 内联错误占位 / 弹窗），根据场景选择合适方案

### Content 状态

- 数据加载成功后正常展示
- 下拉刷新/分页加载等操作中的 loading 应与首次加载区分（如使用局部 loading 而非全屏 loading）

### 状态切换规则

| 当前状态 | 触发操作 | 下一状态 |
|----------|----------|----------|
| 任意状态 | 首次进入页面 | Loading |
| Loading | 请求成功 + 数据非空 | Content |
| Loading | 请求成功 + 数据为空 | Empty |
| Loading | 请求失败 | Error |
| Error | 点击重试 | Loading |
| Content | 下拉刷新 | Content + 局部 loading |
| Content | 加载更多 | Content + 底部 loading |

## 三、通用 UI 规则

### 按钮防重复点击

- 所有触发网络请求或提交操作的按钮，必须在操作进行中禁用
- 操作完成后恢复可点击状态
- 禁用期间展示 loading 态（如按钮内 spinner + "提交中..."文案）

### 输入校验

- 表单提交前必须校验必填项
- 校验失败在对应输入框下方展示错误提示（非弹窗阻断）
- 提交按钮在表单校验通过前保持禁用或点击时触发校验

### 网络异常兜底

- 所有网络请求必须有超时处理
- 超时时间默认 10s，特殊场景可调整
- 超时视为 Error 状态处理
