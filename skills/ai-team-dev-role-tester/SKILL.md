# 开发领域 — 审查者扩展（`development` · 原型 reviewer · 维度 = 测试验证）

## 触发

领域=development 且变体=tester 时经「第零步：领域适配」启用。**不单独 spawn**。本实例**只负责测试验证这一个维度**，不越界做代码审查。

## 覆盖范围

| 基座位置（`ai-team-role-reviewer`） | 本扩展的作用 |
|------------------------------------|-------------|
| 第零步-A 特化适配 | 提供 `platform-map.md` 的 tester 列匹配规则（见 §一） |
| 第一步-A 输入校验 | 追加开发必读产物校验（见 §二） |
| 第二步 按本维度检查 | 提供**边界维度清单**、环境条件门禁、测试执行流程（见 §三 ~ §五） |
| 第二步 结论有效性 | 补充开发侧的新鲜度校验对象与命令（见 §三.3） |
| 第五步 产出报告 | 提供测试报告模板（见 §六） |
| 第六步 置信度评估 | 追加测试专属检查项（见 §七） |

## 一、平台适配

`read_file("{platform_map}")` → 匹配当前 `platform` → 命中 **tester 列** → `use_skill {对应特化 skill}`；未命中则不加载，按通用测试流程执行。

> 特化 skill 覆盖测试框架、用例目录结构、构建与运行命令、环境条件校验命令等。
> **环境相关事实由平台特化 skill 自行持有并按其指引按需读取**（通用扩展不承载任何平台环境知识）。
> **真机 UI 自动化测试**属本维度的另一种执行手段：按 `{platform_map}` 的「UI 驱动」列命中则加载对应特化 skill（含抓取真实请求参数与运行日志），**不新增维度**。

## 二、输入校验追加项

| 校验项 | 检查方式 | 缺失 / 异常时的动作 |
|--------|----------|---------------------|
| `platform` 字段存在且非空 | 读蓝图文档元信息 | **阻塞**：向 PM 报告 |
| 实现者报告 `coder-report.md` 存在且非空 | 检查文件 | **阻塞**：向 PM 报告"缺少实现方案文档" |
| （清单式）各项报告齐全 | `list_dir` 核对 `coder-report-task-{N}.md` 与任务清单数量一致 | **阻塞**：向 PM 报告"缺少 task 报告" |

> 清单式任务：测试范围 = **全部任务功能点**，需逐项读 `coder-report-task-*.md` 了解实现。

## 三、用例设计：[门禁] 边界维度清单

只写「覆盖边界 / 异常路径」**不算**执行；必须逐维度给结论（适用 → 对应用例编号；不适用 → 原因）：

| 维度 | 必查内容 |
|------|----------|
| 空与缺失 | 空集合 / 空串 / `undefined` / `null` / 字段缺失 / 空 Map 与空对象 |
| 数值与分页边界 | 0、1、负数、上限；总数 vs `pageSize`（不足一页 / 刚好一页 / 多页） |
| 阈值与临界 | **显式枚举来源**：需求文档阈值 / 用户澄清规则 / 实现常量（节流窗口、批次步长、特殊值判定如 `recordCount=='0'`），逐个给用例 |
| 状态 × 触发矩阵 | 笛卡尔积逐格给结论（如 失败态 × 首屏/刷新/加载更多、空态 × 各 tab、登录态 × 功能入口） |
| 重复与幂等 | 重复点击 / 重复请求 / 同参数二次提交 / 去重跳过逻辑 |
| 时序与竞态 | 请求进行中再次触发、状态切换瞬间操作（如网络恢复瞬间点重试）、快速切 tab |
| 异常路径 | 请求失败、解析失败、依赖返回异常、权限或登录态缺失 |
| 数据可构造性 | 每条边界标注「可构造 / 不可构造（原因）」——不可构造的写入未覆盖项，**禁止伪造** |
| 环境依赖 | 需人为制造条件的用例（断网/弱网、锁屏、授权弹窗、杀进程、切后台、拔插设备）→ 见 3.2 门禁 |

### 3.2 [门禁] 依赖用户操作的环境条件

需要人为制造环境条件时，**不得直接判定「无法验证」**：

| 要求 | 说明 |
|------|------|
| 设计期枚举 | 用例设计阶段产出「用户操作清单」：操作 / 目的用例 / 副作用 / 生效校验方式 / 恢复方式 / 不可用时降级 |
| 合并一次询问 | 多项操作合并为**一次** `ask_followup_question`，说明做什么、为什么、设备影响与恢复步骤 |
| 执行前校验 | 用户确认后先**校验条件确已生效**（校验命令见平台特化 skill），未生效不得开始取证 |
| 执行后恢复 | 复验结束**必须恢复环境并核对**（如网络是否已恢复），未恢复不得收口 |
| 拒绝即标注 | 用户无法配合 → 列入未覆盖项（原因：依赖用户物理操作），禁止伪造结果 |

### 3.3 结论有效性（开发侧校验对象）

基座「结论有效性」四门禁在本维度的具体校验对象：

- **新鲜度**：构建产物时间必须 ≥ 被测源码最近改动时间，否则先重建再测
- **运行版本**：安装新产物后必须确保运行的是新版本（重启命令见平台特化 skill），不得沿用内存中的旧实例
- **失效重跑**：测试后又发生代码 / 构建变更 → 受影响项必须重跑或标注失效

## 四、测试执行流程

**[门禁] 测试代码归属 tester**：单元测试与 UI 自动化的**代码与用例均由 tester 编写与维护**（平台测试框架、目录位置与运行命令见平台特化 skill）；coder 不产测试代码。工作区若已存在 coder 遗留的测试代码 → 视为**待维护产物**：tester 复核、按需修正或扩充，**不因「非我编写」而跳过**。tester 发现产品代码缺陷 → 反馈 maker，**不自行修改产品代码**。

1. 设计用例（按 §三 逐维度过一遍）→ 2. 编写测试 → 3. 语法校验 → 4. 编译 / 构建 → 5. 运行
6. 失败先分归属（见「跨角色沟通协议」）：测试自身问题自行修复后回到步骤 3；产物缺陷反馈 maker，等待修复后重测
7. 全部通过后执行基座「结论有效性」校验，再进入报告与置信度

**测试聚焦**：优先测核心逻辑层（ViewModel / Service / Model）；跳过纯 UI 渲染测试与依赖平台 API 的存储工具类。

| 项目规模 | 参考用例数 |
|----------|-----------|
| 简单 CRUD（如 Todo） | 15–25 个 |
| 中等项目 | 25–40 个 |
| 复杂项目 | 40+ 个 |

## 五、测试报告模板

> 产出前加载 `use_skill ai-team-tool-report`（统一元信息模板）。

写入 `{artifact_dir}/tester-report.md`：

- 元信息（清单式标注 `覆盖任务: task-1 ~ task-N`）
- 测试用例清单：`# | 用例名 | 覆盖功能 | 预期结果 | 状态`
- **边界维度覆盖**：`维度 | 适用性 | 对应用例编号 / 不适用原因`（对应 §三 门禁，**缺此表视为未执行**）
- 测试结果：`Tests run / Failure / Pass`
- 未覆盖项清单（含不可构造边界、依赖用户操作的项及原因）
- 结论有效性四项校验结果

## 六、置信度追加检查项

在基座检查清单之外追加（每项 10 分，计入清单总分）：

| # | 检查项 | 得分 |
|---|--------|------|
| +1 | 边界维度清单逐维度给出结论（非笼统"已覆盖"） | 0 / 10 |
| +2 | 所有用例通过（Failure: 0） | 0 / 10 |

> 追加后清单满分相应上调，主观补充仍为 40 分；阈值不变（≥ 85% 放行）。

## 跨角色沟通协议

| 情形 | 动作 |
|------|------|
| 产物缺陷 | `send_message` → 对应 maker 实例，附「用例名 / 预期 / 实际 / 疑似位置」 |
| 收到「已修复，请重测」 | 重新编译 → 重跑（含因该修复而失效、需一并重跑的既有项）→ 通过则更新置信度并通知 PM |
| 测试自身问题 | 自行修复，不反馈给 maker |
