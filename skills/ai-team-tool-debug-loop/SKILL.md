# 协作调试循环

## 触发

由调用方在 bug 修复且根因不明时按需加载（调用方自行判定）。

## 核心问题

AI 难以自行复现**部分** bug（取决于平台：鸿蒙可经 `hdc` / 真机 UI CLI 自主驱动链路，Web/端侧交互往往仍需用户当"操作手"）。需人机协作：AI 作"诊断脑"，必要时用户作"操作手"。

> **[门禁] 日志是强手段，但不是首选**：运行时日志（真机尤其）是**证据力最强**的定位手段，但它的**成本也最高**——改代码 → 编译 → 安装 → `force-stop` 重启 → 再复现，一轮很贵。**必须先按下方成本阶梯穷举低成本手段，确证不足时才埋点。**

## 步骤 0：定位手段选择（成本递增，先试低成本的）

| 序 | 手段 | 适用 | 成本 |
|---|------|------|------|
| 1 | **代码路径推理** | 分支/判空/时序/边界等逻辑类 bug，读代码即可证伪或定位 | 0 |
| 2 | **已有日志**：项目自带 hilog / 埋点 / HTTP 请求 URL 日志 / 崩溃日志 | 多数"数据不对、请求没发对、改动没生效"类问题 | 0（不改代码） |
| 3 | **自动化复现**：ohosTest 单测（可固化行为）/ 真机 UI CLI 驱动链路（`ai-team-dev-pt-hm-ui-test`，含抓请求参数） | 需真实链路或运行时参数，但不该让用户手操 | 低~中（仅构建/驱动） |
| 4 | **新增最小化诊断日志**（本 skill 主流程） | 1~3 均无法解释，必须看运行时中间值 | 高（改码+重装+复现） |
| 5 | **二分 / 回滚定位**（git bisect、版本对照、开关对照） | 「曾经正常，某次改动后异常」 | 中 |

> **[门禁] 不得跳过 1~3 直接埋点**；也不得停在 1 就断言根因——1 只能提出假设，需 2/3/4 任一项提供运行时证据才能定性。
> **用户操作优先**：若某一步"用户点一下就能完成、AI 自己绕很多步"，先给选项让用户做（见 `ai-team-tool-global-rule`「用户协作成本优先」）。

## 调试循环

```
分析代码 → 埋点日志 → 指导用户复现 → [等待用户确认]
    ↑                                        ↓
    ←←← 未定位根因 ←← 读取日志+用户描述 ←← 诊断
    ↓
  定位根因 → 修复 → 清理日志 → 交回调用方继续验证
```

> 上图为「步骤 0 手段 1~3 无法定位」之后才进入的主循环；若代码推理或已有日志已能定性，**不要进入埋点循环**（否则白付一轮构建 + 复现成本）。

### 步骤 1：分析 + 埋点（最小化）

> 进入本步骤的前提：步骤 0 的手段 1~3 已确证不足。

1. 读取用户 bug 描述，定位可疑代码区域
2. 在关键路径添加**最小化**诊断日志（只埋能区分假设的点，避免日志淹没关键信息）：
   - 函数入口/出口：记录参数、返回值
   - 条件分支：记录走了哪个分支
   - 状态变更：记录变更前后的值
   - 异常捕获：记录完整 error stack
3. 日志需带统一前缀（如 `[DEBUG-LOOP]`），便于后续过滤
4. 编译确保日志代码无误

> 平台特化 skill 可补充具体日志 API（如鸿蒙 hilog、Web console、Node util.log）。

### 步骤 2：复现（优先 AI 自主，其次用户）

**复现优先由 AI 自行完成**：鸿蒙可经 `hdc` / 真机 UI CLI（`ai-team-dev-pt-hm-ui-test`）驱动点击、滑动并抓取日志与请求 URL；仅当无法自主驱动（如需人脸/支付/外部 App 交互、依赖用户独占的账号态）时才交用户手操。

交由用户时，用 `ask_followup_question` 告知操作步骤并等待确认：

```
标题: "协作调试"
问题: "已添加诊断日志。请按以下步骤操作复现问题：\n{具体操作步骤}\n操作完成后选择："
选项: ["我已操作完成", "无法复现该问题", "操作中发现其他异常"]
```

> **[门禁] 操作步骤必须具体可执行**，不写"请复现问题"这种模糊指令。应写明：打开哪个页面 → 点击什么按钮 → 输入什么内容 → 预期 vs 实际现象。

### 步骤 3：读取日志 + 用户描述

用户确认后：

1. **读取日志文件**：按平台方式获取日志，过滤 `[DEBUG-LOOP]` 前缀的相关条目
2. **解析用户选择**：

| 用户选择 | 处理方式 |
|----------|----------|
| 我已操作完成 | 直接读取日志，进入诊断 |
| 无法复现该问题 | 询问用户上次成功复现的条件（操作序列/环境/数据），调整埋点范围后回到步骤 1 |
| 操作中发现其他异常 | 将用户描述的异常作为新线索，结合日志一起分析 |
| 末位自定义项 / 用户自由描述 | 读取用户描述的 bug 现象，结合日志一起分析 |

> **[门禁] 必须实际读取日志文件，严禁凭空猜测日志内容。** 日志读取失败时按异常处理标准化（告知用户/降级继续）。

### 步骤 4：诊断

结合日志数据和用户描述，分析根因：

- 日志显示异常值/错误 → 定位到具体代码行
- 日志显示流程异常（走了不该走的分支）→ 定位逻辑错误
- 日志无明显异常 → 扩大埋点范围，回到步骤 1

### 步骤 5：修复

1. 根据诊断结果修复代码
2. **移除诊断日志**（或保留为正式日志，若对后续维护有价值）
3. 交回调用方主流程，由其继续后续验证环节

## 迭代控制

| 轮次 | 动作 |
|------|------|
| 第 1-2 轮 | 正常埋点 → 复现 → 诊断 |
| 第 3 轮 | 若仍未定位，扩大埋点范围 + 询问用户更多细节（操作截图/视频/环境信息） |
| 超过 3 轮 | 停止循环，把当前进展与发现交回调用方，由其决定是否请用户提供更多信息 |

## 平台日志读取参考

| 平台 | 日志来源 | 读取方式 |
|------|----------|----------|
| harmony | hilog / 应用沙箱日志文件 | `hdc shell hilog -b D`（放开级别）→ `hdc shell hilog -r`（清缓冲）→ 复现 → `hdc shell hilog -x -n 4000` 过滤 `[DEBUG-LOOP]`（实测可用，细节见 `ai-team-dev-pt-hm-ui-test`） |
| web | 浏览器控制台 / Network | 用户手动复制 / DevTools 导出 |
| node | 终端输出 / 日志文件 | 直接读取日志文件 |
| 其他 | 按平台约定 | — |

> 平台特化 skill 可覆盖此表，提供更精确的日志读取命令。
