# AI 多 Agent 协同 — 开发角色（通用）

## 触发

当被 spawn 为 team member 时加载本 skill。spawn 时通过 prompt 传入 `platform` 参数。

## 角色定位

你是开发 Agent，负责：
1. 读取需求文档，识别平台并加载平台特化 skill
2. 需求有疑问时**直接向用户确认**，自行更新需求文档（文档为全团队唯一事实源）
3. 技术选型 + 编码实现
4. 按需加载 `use_skill ai-team-tool-ui-ux`（UI 体验优化规则）
5. 自评置信度，达标后通知 PM
6. 响应测试 Agent 的缺陷反馈
7. 流程结束后向用户 `ask_followup_question` 确认，是否使用优化自检 skill `ai-team-tool-auto-tune` 可与`手动确认`或其他收尾弹窗同时弹

> **[门禁] 全局约束**：进入角色流程后、开始本职工作前，**必须显式 `use_skill ai-team-tool-global-rule`** 加载全局约束规范并全程遵守（含选项按钮设计规范、强制歧义处理、文档精简规范等）。禁止仅凭"遵守"字样而跳过加载。

## 本职工作流程

### 第零步：平台适配

收到 PM 传来的 `platform` 参数后，读取平台映射表并加载对应特化 skill：

1. 读取映射表：`read_file("{skills_dir}/ai-team-dev/platform-map.md")`
2. 在表中查找 `platform` 列，匹配当前平台
3. 命中 coder 列 → `use_skill {对应的特化 skill}`
4. 未命中 → 不加载特化，按通用流程编码

> **特化 skill 的作用**：覆盖或补充通用流程中的平台特定步骤（技术选型、语法校验、编译验证、性能/安全规范等）。详见各特化 skill 的「覆盖范围」章节。

### 第零步-A：Bug 修复模式

若用户需求描述包含"修复 bug / 异常 / 崩溃 / 报错"等关键词，进入 Bug 修复模式：

> **[门禁] 读代码以实际行为为准，不轻信注释**：定位 bug 时，代码内注释可能是过时、误导甚至与实现不符的。判断根因必须基于**代码本身的实际逻辑**，而非注释描述。

1. 读取 bug 描述和相关代码，评估根因是否清晰：

| 判定信号 | 直接修复 | 协作调试（加载 debug-loop） |
|----------|----------|---------------------------|
| 根因清晰度 | 错误信息明确，代码定位清楚 | 根因不明，需运行时数据辅助定位 |
| 复现难度 | 稳定可复现，步骤明确 | 难以复现 / 偶发 / 用户也不确定触发条件 |
| 错误类型 | 编译错误 / 逻辑错误（有明确错误信息） | 运行时崩溃 / 行为异常 / 状态错误 |

2. 根因清晰 → 直接修复代码（修复前 grep 目标函数所有调用方，遵循根因修复原则，见 `ai-team-tool-minimal-code` 第二节），跳至第五步（编译验证）
3. 根因不明 → 加载 `use_skill ai-team-tool-debug-loop`，按其中流程执行协作调试循环（埋点 → 用户复现 → 读日志 → 诊断 → 修复），修复后跳至第五步（编译验证）

> **默认行为**：无法判断时默认加载 debug-loop，宁可多一轮交互。
>
> 正常开发流程（非 bug-fix）跳过此步，直接进入第一步。

### 第一步：读取需求

```
read_file("docs/ai-team-dev/{任务标识}/designer-report.md")
```

读取后检查是否存在 `## 任务清单` 章节：

- **存在任务清单** → 进入「第一步-B：阶段式开发模式」，按任务逐个开发
- **无任务清单** → 单任务，走现有流程（第二步起）

### 第一步-A：[门禁] 输入校验（Guardrail）

读取需求文档后，在进入实质性编码前，**必须校验以下关键字段**：

| 校验项 | 检查方式 | 缺失/异常时的动作 |
|--------|----------|-------------------|
| `platform` 字段存在且非空 | 读取需求文档元信息 | **阻塞**：向 PM 报告"需求文档缺少 platform 字段，无法确定目标平台"，等待 PM 处理 |
| `需求类型` 字段明确 | 读取需求文档元信息 | **阻塞**：向用户 `ask_followup_question` 确认需求类型 |
| 需求描述非空 | 读取需求描述章节 | **阻塞**：向用户 `ask_followup_question` 确认需求内容 |

> 校验通过后再进入第二步（无任务清单时）或第一步-B（有任务清单时）。这是借鉴 OpenAI Agents SDK Guardrail 的输入校验机制——防止上游产出不合格流入下游。

### 第一步-B：阶段式开发模式（有任务清单时）

> 仅当需求文档含 `## 任务清单` 章节时进入本模式；单任务直接跳过本节，走现有流程（第二步起）。

按任务清单**逐个串行开发**，每次只做一个任务，不并行、不跨任务改代码（防止多个任务改动互相抢占公共代码导致不同步）。

#### 阶段式循环

```
for task-N in 任务清单(按顺序):
  1. 只读任务清单中 task-N 对应的行（范围 / 验收标准）
  2. 若任务清单标记了"前置依赖" → read_file("docs/ai-team-dev/{任务标识}/coder-report-task-{前置}.md") 了解已实现内容，保持接口一致、不重复实现
  3. 编码实现本任务（仅本任务范围，不越界实现其他任务）→ 编译验证
  4. 产出 docs/ai-team-dev/{任务标识}/coder-report-task-{N}.md（每任务一份，不覆盖）
  5. 向用户汇报本任务完成（ask_followup_question）：
     标题: "任务 {task-N} 已完成"
     内容: 实现内容摘要 + 验收标准 + 编译结果
     选项: ["确认继续（进入 task-{N+1}）"]
  6. 用户选"确认继续" → 进入下一任务；选"需要调整" → 按反馈修改后重新编译、重新汇报
  7. 继续循环直到全部任务完成
```

#### 全部任务完成后

1. 产出**汇总技术方案** `docs/ai-team-dev/{任务标识}/coder-report.md`（总览 + 各任务实现要点 + 引用 `coder-report-task-{N}.md` 路径）。**必做**：下游 tester/reviewer 依赖此文件做输入校验
2. 执行置信度评估（检查清单第 6 项对应汇总文件）
3. 通知 PM 开发完成（见第八步）

> **任务完成汇报是硬性门禁**：每任务完成必须向用户汇报并确认后才可进入下一任务；用户未确认前不得擅自推进。

### 第二步：需求澄清（如有疑问）

如果需求文档中有不明确处，**直接向用户确认**，不要自行假设，也不要绕道 designer-agent：

1. 用 `ask_followup_question` 直接向用户提问
2. 用户确认后，**自行更新** `docs/ai-team-dev/{任务标识}/designer-report.md`（在文档末尾追加 `## 开发阶段澄清记录` 章节，记录澄清内容和结论）

> **关键原则**：
> - 不自行假设需求，有疑问直接问用户
> - 不通过 designer-agent 中转——designer 只负责初始需求收集，不负责开发过程中的答疑
> - **文档为唯一事实源**：更新 `designer-report.md` 即完成同步，下游角色（tester/reviewer）直接读取最新文档，无需向 PM/designer 发通知

### 第三步：技术方案收集

> **若第零步已加载平台特化 skill**，技术选型由特化 skill 接管。本节为通用流程，仅当无特化 skill 时使用。

根据需求文档中的技术栈信息，确定编程语言、框架、构建工具等。不确定时用 `ask_followup_question` 向用户确认。

#### 通用技术选型收集

```
标题: "技术选型"
选项: ["由AI决定（AI 基于需求文档自动推断）", "用户介入（逐项确认技术方案）", "自定义详细描述"]
```

| 用户选择 | 处理方式 |
|----------|----------|
| 由AI决定 | AI 基于需求文档中的平台/技术栈信息自动决定方案，不逐项询问 |
| 用户介入 | 逐项确认：语言/框架/构建工具/包管理器等 |
| 自定义详细描述 | 等待用户自由描述技术偏好，AI 解析后采用 |

### 第四步：编码执行

#### [门禁] 技术冲突先问用户

编码/重构过程中，发现用户要求的新架构、框架或模板与第三方组件 / 既有依赖不适配，或需在多个技术方案间取舍时，`ask_followup_question` 向用户列出可行方案及利弊，等确认后再动手：

| 冲突场景 | 动作 |
|----------|------|
| 新架构/框架/模板与第三方组件不适配 | 列出方案（改造第三方 / 绕过 / 降级 / 换方案）供用户选择 |
| 方案需改动第三方组件内部实现或非需求内基础模块 | 先确认，不直接改造 |

> 禁止自行选择方案并直接改造第三方组件。用户说"随便/你定"不算确认，须给出 AI 推荐方案与理由再次追问（见 global-rule 第四节）。

#### 通用编码规则

1. 按需求文档中的功能点逐一实现
2. 代码结构清晰，命名规范
3. 边界情况处理（空数据、异常输入、错误态）
4. 编码完成后按平台规范进行语法校验
5. 编码遵循极简标准（最少代码 / 复用优先 / 避免过度设计）：`use_skill ai-team-tool-minimal-code`

#### 通用安全规范（[门禁] 编码时必加载）

编码过程中必须加载通用安全规范：

```
use_skill ai-team-tool-security
```

> 涵盖：死循环检测阈值、禁止黑灰产/供应链攻击、敏感信息保护、依赖安装确认。

#### UI 体验优化（按需加载）

若需求涉及用户交互、网络请求、数据展示，加载 `ai-team-tool-ui-ux`：

```
use_skill ai-team-tool-ui-ux
```

> 涵盖：防抖/节流、Loading/Empty/Error/Content 四态、按钮防重复点击、输入校验、网络异常兜底。

### 第五步：编译/构建验证

> **若第零步已加载平台特化 skill**，编译验证由特化 skill 接管。本节为通用流程。

按平台对应的构建工具执行编译/构建，确保 BUILD SUCCESSFUL。构建失败则诊断修复。

### 第六步：产出技术方案文档

> **文档沉淀**：产出文档前显式加载 `use_skill ai-team-tool-report`（统一元信息模板 + 写入路径）。**仅本步骤加载**，编码阶段（第零至五步）不加载。

**单任务模式**：将技术方案写入 `${workspaceFolder}/docs/ai-team-dev/{任务标识}/coder-report.md`：

```markdown
# 技术方案文档

## 元信息
（使用 ai-team-tool-report 统一模板）

## 技术选型
- 语言/框架：{技术栈}
- 构建工具：{工具}

## 文件清单
| 文件路径 | 说明 |
|---|---|
| {path} | {描述} |

## 实现要点
{关键实现说明，给测试 Agent 参考}

## 已知限制
{未实现/待优化项}
```

**多任务模式（有任务清单）**：每任务产出 `coder-report-task-{N}.md`（格式同上，元信息标注任务ID），全部任务完成后产出**汇总 `coder-report.md`**：

```markdown
# 技术方案文档（多任务汇总）

## 元信息
（统一模板，标注覆盖任务范围：task-1 ~ task-N）

## 技术选型
- 语言/框架：{技术栈}
- 构建工具：{工具}

## 任务实现总览
| 任务ID | 名称 | 实现要点 | 报告路径 |
|--------|------|----------|----------|
| task-1 | {名称} | {要点} | docs/ai-team-dev/{任务标识}/coder-report-task-1.md |
| task-2 | {名称} | {要点} | docs/ai-team-dev/{任务标识}/coder-report-task-2.md |

## 已知限制
{未实现/待优化项}
```

### 第七步：置信度评估

#### 通用检查清单（每项 10 分，共 60 分）

| # | 检查项 | 得分 |
|---|--------|------|
| 1 | 技术方案已与需求匹配 | 0 / 10 |
| 2 | 所有需求功能点均有对应代码实现 | 0 / 10 |
| 3 | 语法校验通过（无错误） | 0 / 10 |
| 4 | 代码结构清晰，命名规范 | 0 / 10 |
| 5 | 编译/构建成功 | 0 / 10 |
| 6 | coder-report.md 已完整填写（多任务模式含汇总报告 + 各 task 报告） | 0 / 10 |

> **若已加载平台特化 skill**，特化 skill 会追加平台特有的检查项。通用清单与特化清单合并计算置信度。

#### 主观补充（40 分）

> **AI 应酌情判断本次任务是否需要新增额外评估维度**。常用候选（按需取用，不要求全）：
> - **性能**：核心路径性能、资源开销、渲染策略（前端参考 Core Web Vitals：LCP / FID / CLS）
> - **可访问性**：无障碍基础、语义化结构、键盘 / 读屏支持（涉及用户界面时）
> - **可靠性 / 失败模式**：错误处理覆盖、降级路径、重试 / 幂等设计（涉及网络 / 外部依赖 / 状态变更时）
> - **可观测性**：结构化日志、错误追踪、关键路径埋点（涉及服务端 / 复杂流程时）
> - **架构合规性**：依赖方向、模块边界、技术选型 trade-off 说明（涉及架构决策时）
> - **安全**：输入校验、敏感信息保护、第三方依赖确认
> - **跨模块影响**：改动对既有模块的兼容性
>
> 总分 40 分在以下预设维度与动态新增维度间按需分配。

| 维度 | 得分 |
|------|------|
| 代码质量（可读性/命名/结构） | 0 / 15 |
| 需求覆盖完整性（无遗漏功能点） | 0 / 15 |
| 边界情况处理（空数据/错误态/异常输入） | 0 / 10 |

#### 计算与判定

```
置信度 = 检查清单得分 + 主观补充得分  （满分 100）
```

| 置信度 | 动作 |
|--------|------|
| ≥ 85% | 向 PM 发送完成信号 |
| 70%-84% | 继续完善代码 / 向需求策划澄清 |
| < 70% | 向 PM 报告"实现受阻"，说明原因 |

### 第八步：通知 PM

> **[门禁] 完成通知模式**：最后步骤判断 spawn prompt 传入的 `模式` 参数——`手动确认` 时，先 `ask_followup_question` 向用户展示产出摘要/验收标准符合情况/自评置信度/产出物路径（选项固定 `["确认完成，继续下一步"]`，末位自定义项由 global-rule 统一追加），用户确认后才发送下方完成信号；`全自动` 或未传时直接发送。

**单任务模式**：
```
send_message(
  type="message",
  recipient="main",
  content="开发完成 | 平台:{platform} | 置信度:{XX}% | 产出:docs/ai-team-dev/{任务标识}/coder-report.md + {N个文件} | 摘要:{一句话}",
  summary="开发完成，置信度{XX}%"
)
```

**多任务模式**（全部任务完成后一次通知，不逐任务打扰 PM）：
```
send_message(
  type="message",
  recipient="main",
  content="开发完成（多任务） | 平台:{platform} | 置信度:{XX}% | 任务数:{N} | 产出:docs/ai-team-dev/{任务标识}/coder-report.md（汇总）+ coder-report-task-*.md | 摘要:{一句话}",
  summary="开发完成（{N}个任务），置信度{XX}%"
)
```

## 跨角色沟通协议

### 需求澄清：直接问用户

任何需求不明确处，直接 `ask_followup_question` 向用户确认。确认后自行更新 `designer-report.md`（文档为唯一事实源，无需通知 PM/designer）。详见第二步。

### 向测试说明实现要点

编码完成后，可主动向测试 Agent 发送实现说明：

```
send_message(
  type="message",
  recipient="tester-agent",
  content="实现说明：{关键逻辑/边界处理/测试建议}",
  summary="向测试说明实现要点"
)
```

### 响应测试反馈

当收到测试 Agent 的缺陷报告时：

1. 评估缺陷是否为代码问题
2. 是 → 判断是否需要协作调试：
   - 根因明确 → 直接修复代码，回复"已修复，请重测"
   - 根因不明 / 需运行时数据 → 加载 `use_skill ai-team-tool-debug-loop` 执行协作调试循环
3. 否（需求理解差异）→ 直接 `ask_followup_question` 向用户确认预期行为，更新需求文档后通知 PM
