# 开发领域 — 实现者扩展（`development` · 原型 maker · 变体 coder）

## 触发

由 `ai-team-role-maker` 在 `领域=development` 时经「第零步：领域适配」加载。**不单独 spawn**，仅补全/覆盖基座中标 `[领域扩展]` / `[特化]` 的步骤。

## 覆盖范围

| 基座位置（`ai-team-role-maker`） | 本扩展的作用 |
|----------------------------------|-------------|
| 第零步-A 特化适配 | 提供 `platform-map.md` 的 coder 列匹配规则（见 §一） |
| 第零步-B 返工模式分流 | 提供根因清晰度与复现难度的判定信号（见 §二） |
| 第一步-A 输入校验 | 追加开发必填字段校验（见 §三） |
| 第一步-B 清单式分批产出 | 提供任务清单来源、任务粒度与报告命名（见 §四） |
| 第三步 实现方案确定 | 提供技术选型收集流程（见 §五） |
| 第四步 产出 | 追加语法校验、技术冲突门禁与按需工具（见 §六） |
| 第五步 产物验证 | 提供编译/构建验证标准（见 §七） |
| 第六步 产出报告 | 提供开发报告模板（见 §八） |
| 第七步 置信度评估 | 追加开发专属检查项（见 §九） |

## 一、平台适配

`read_file("{platform_map}")` → 匹配当前 `platform` → 命中 **coder 列** → `use_skill {对应特化 skill}`；未命中则不加载，按通用编码流程执行。

> 特化 skill 覆盖或补充本扩展中的平台特定步骤（技术选型、语法校验、编译验证、性能 / 安全规范等）。

## 二、返工模式判定信号

| 判定信号 | 直接修复 | 协作调试（加载 `ai-team-tool-debug-loop`） |
|----------|----------|-------------------------------------------|
| 根因清晰度 | 错误信息明确，代码定位清楚 | 根因不明，需运行时数据辅助定位 |
| 复现难度 | 稳定可复现，步骤明确 | 难以复现 / 偶发 / 用户也不确定触发条件 |
| 错误类型 | 编译错误 / 逻辑错误（有明确错误信息） | 运行时崩溃 / 行为异常 / 状态错误 |

> **[门禁] 读代码以实际行为为准，不轻信注释**：代码内注释可能过时、误导甚至与实现不符；判断根因必须基于**代码本身的实际逻辑**。
> **默认行为**：无法判断时默认加载 debug-loop，宁可多一轮交互。

## 三、输入校验追加项

| 校验项 | 检查方式 | 缺失 / 异常时的动作 |
|--------|----------|---------------------|
| `platform` 字段存在且非空 | 读蓝图文档元信息 | **阻塞**：向 PM 报告"缺少 platform 字段，无法确定目标平台" |
| 需求类型字段明确 | 读蓝图文档元信息 | **阻塞**：`ask_followup_question` 向用户确认 |
| 需求描述非空 | 读蓝图文档 | **阻塞**：`ask_followup_question` 向用户确认 |

## 四、任务清单式分批产出

**清单来源**：蓝图文档 `## 任务清单` 章节（由 `ai-team-dev-role-designer` 触发拆分时产出），每项 = 一个**可独立完成并独立编译验证的交付单元**。

- **有任务清单** → 按基座第一步-B 逐项串行开发，每项报告产 `{artifact_dir}/coder-report-task-{N}.md`（不覆盖）
- **无任务清单** → 单任务；完成时**若为常规及以上工作量**产 `{artifact_dir}/coder-report.md`
- **小改动**（PM 在 spawn prompt 标注 `小改动`）→ 直接实现完成，**不产报告**

> 每项开发前若任务清单标注了「前置依赖」→ `read_file("{artifact_dir}/coder-report-task-{前置}.md")`，保持接口一致、不重复实现。
> 全部完成后产**汇总** `coder-report.md`（总览 + 各项要点 + 引用各项报告路径）——**下游 tester / reviewer 依赖它做输入校验**。

## 五、技术选型收集

| 用户选择 | 处理方式 |
|----------|----------|
| 由 AI 决定 | 基于蓝图中的平台 / 技术栈信息自动决定，不逐项询问 |
| 用户介入 | 逐项确认：语言 / 框架 / 构建工具 / 包管理器等 |
| 自定义详细描述 | 等用户自由描述技术偏好，AI 解析后采用 |

```
标题: "技术选型"
选项: ["由AI决定（AI 基于需求文档自动推断）", "用户介入（逐项确认技术方案）"]
```

## 六、产出追加要求

1. 编码完成后按**平台规范执行语法校验**
2. 若需求涉及用户交互、网络请求、数据展示 → 按需加载 `use_skill ai-team-tool-ui-ux`（防抖 / 节流、四态管理、防重复点击、输入校验、网络异常兜底）

**[门禁] 技术冲突先问用户**：

| 冲突场景 | 动作 |
|----------|------|
| 新架构 / 框架 / 模板与第三方组件不适配 | 列出方案（改造第三方 / 绕过 / 降级 / 换方案）供用户选择 |
| 方案需改动第三方组件内部实现或非需求内基础模块 | 先确认，**不直接改造** |

## 七、编译验证 + 最小冒烟自验

1. **编译**：按平台对应的构建工具执行编译 / 构建，确保 **BUILD SUCCESSFUL**；失败则诊断修复后重验。具体命令见平台特化 skill
2. **最小冒烟自验**：安装产物并启动，核心流程走通一次（证明产物可用，而非仅可编译）；具体命令见平台特化 skill

> **[门禁] coder 不写测试**：coder **不编写单元测试 / UI 自动化测试**，**不建测试目录、不产测试文件、不产测试用例** —— 测试的代码与用例均归 tester 维度编写与维护（平台测试框架与目录位置见平台特化 skill）。coder 只在冒烟自验中做一次端到端走通与崩溃扫描。
> **默认行为**：无设备 / 无法安装时，如实登记「未做冒烟自验（原因）」，**不得伪造**，也不得为凑验证而改去写测试。

## 八、开发报告模板

> 产出前加载 `use_skill ai-team-tool-report`（统一元信息模板）。

```markdown
# 技术方案文档
## 元信息 （统一模板；清单式标注覆盖范围 task-1 ~ task-N）
## 技术选型
- 语言/框架：{技术栈}     构建工具：{工具}
## 文件清单
| 文件路径 | 说明 |
## 任务实现总览 （仅清单式：任务ID / 名称 / 实现要点 / 报告路径）
## 实现要点
{关键实现说明，给测试与审查参考}
## 已知限制
{未实现 / 待优化项}
```

## 九、置信度追加检查项

在基座检查清单之外追加（每项 10 分，计入清单总分）：

| # | 检查项 | 得分 |
|---|--------|------|
| +1 | 语法校验通过（按平台规范，无错误） | 0 / 10 |
| +2 | 编译 / 构建成功 | 0 / 10 |
| +3 | 最小冒烟自验通过（可安装启动 + 核心流程走通一次） | 0 / 10 |

> 追加后检查清单满分相应上调，主观补充仍为 40 分；阈值不变（≥ 85% 放行）。
> 无设备导致冒烟自验无法执行时，该项按 0 分计入并如实登记原因（**不得**改用「写了测试」补分）。
