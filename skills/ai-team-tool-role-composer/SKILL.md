# AI 多 Agent 协同 — 角色组合器

## 触发

本 skill 在以下**两个时机**取用：

| 时机 | 用途 | 产出去向 |
|------|------|----------|
| **阶段 1.0-A 预估推导** | 为生成弹窗选项，基于**用户原始问题**推导候选角色清单 | 仅填入选项文字；**不落盘、不传递** |
| **阶段 2.2 权威定义** | 基于**最终清单**为每个角色明确四要素 | 用于 spawn prompt |

> **计划者为预设角色（非动态推导）**：用户在 1.0 Q1 **勾选「计划者」**时，内核 1.1 / 领域 PM 1.2 按固定模板直接 spawn，**无需加载本 skill**；**未勾选**时该环跳过（预估清单即最终清单，见内核实 1.3）。已命中领域（`development` / `writing`）的角色由该领域 `role-registry.md` 定义，不走本 skill。
>
> **[门禁] 预估 ≠ 权威**：1.0-A 的预估清单仅供用户看，可能被 designer 修正；2.2 必须以下发来的「最终清单」为准，不得用预估清单覆盖。

### 预估推导 vs 权威推导

| | 1.0-A 预估推导 | designer / 2.2 权威推导 |
|---|---|---|
| 输入 | 用户原始问题 | 深挖后的需求 |
| 精度 | 粗（推测性） | 高（可独立验收） |
| 是否落盘 | 否 | 是（designer-report） |
| 与用户确认 | 通过弹窗选项 | designer 直接确认 |
| 可否被覆盖 | 是（designer 可修正） | 否（最终事实源） |

> 用户**未勾选「计划者」**时，预估推导即成为权威（无计划者兜底），此时需在 2.2 复用同一份清单。

## 一、核心定位

本 skill 提供「如何创建正确角色」的**推导方法**与**约束**，不提供角色清单。

> 角色不是职位、不是预设清单里的选项，而是「一个独立视角 × 一个可独立验收的子目标」的**职责容器**。正确的角色从问题本身长出来，而非从目录里挑出来。
>
> **落位要求**：推导出的每个角色**尽量落位到三个原型之一**（见次节）。确实无法归入原型时，才作为纯动态角色由 PM 在 spawn prompt 内联职责。

## 二、三个角色原型（推导的落位词汇表）

| 原型 | 基座 skill | 定位 |
|------|-----------|------|
| 计划者 | `ai-team-role-planner` | 澄清需求、拆解子目标、产出蓝图与口径，是内容口径的权威定义方 |
| 实现者 | `ai-team-role-maker` | 按蓝图产出最终交付物 |
| 审查者 | `ai-team-role-reviewer` | 按指定维度检查把关；**可多实例**（每维度一个实例） |

> **落位规则**：子目标需要「定义口径」→ 计划者；「产出交付物」→ 实现者；「检查把关」→ 审查者。同类子目标合并为同一实例；审查类子目标按**维度**拆为多个实例。
> 领域模式下（`development` / `writing`），可用原型与变体以该领域 `role-registry.md` 为准，**不得自行发明变体名**。

### 预设前置角色：计划者

| 要素 | 定义 |
|------|------|
| 角色 | 原型 `planner`（基座 `ai-team-role-planner`；`generic` 时无领域变体） |
| 职责 | 深入研究需求、拆解子目标、适配角色清单、产出蓝图（详见基座 skill） |
| 产出物 | `{artifact_dir}/designer-report.md`（全团队唯一事实源，下游角色直接读取） |
| spawn 时机 | **预设但可选**；`mode="plan"`；PM 禁止自行调研需求 |

> **定位说明**：先有清晰需求才能正确推导后续角色，故计划者作为**预设前置角色**（其角色定义不依赖问题内容）。其余角色走动态推导 + 原型落位。

## 三、何时值得拆出一个角色

一个子目标是否值得独立成角色，看它是否满足以下任一信号，且带来的收益超过成本（每角色 = 独立 context + 独立 token）：

| 信号 | 说明 |
|------|------|
| 视角独立 | 需要与其他角色不同的专业视角或立场，差异能带来补充或制衡价值 |
| 产出独立 | 子目标可独立完成、独立验收，不依赖他人过程 |
| 上下文隔离 | 体量大或信息面广，独立 context 能避免污染主上下文 |

> 三个信号都不满足 → 不拆角色，由单 Agent 顺序完成。

## 四、角色推导方法（动态）

```
问题
 ↓
[1] 拆解为子目标（2-5 个，按「可独立完成、可独立验收」，不预设角色）
 ↓
[2] 对每个子目标自问：高质量完成它，需要什么视角/专业/立场？
 ↓
[3] 视角相同 → 合并为同一角色；视角不同 → 各自独立成角色
 ↓
[4] 从子目标反推角色职责，而非从预设清单选角色
 ↓
[5] 检查职责边界（无重叠 / 无遗漏 / 无越界）与依赖拓扑
 ↓
[6] 数量 >5 或职责重叠 → 回退合并子目标后重来
```

> **关键原则**：角色是从「子目标需要什么视角」反推出来的，不是先想「有哪些角色可用」再套任务。

## 五、角色定义规范

每创建一个角色，必须明确四要素：

| 要素 | 要求 |
|------|------|
| 角色名 | 从职责提炼（如「调研者」「评审者」），同任务内唯一，避免用头衔堆砌 |
| 职责 | 一句话说明「做什么 + 边界在哪」，不写过程 |
| 产出物 | 写入 `docs/ai-team/{role}-report.md`，单写多读 |
| 验收标准 | 可验证的完成条件（含格式、内容、来源要求） |

> 未预设角色无独立 skill，spawn 时由 PM 内联职责（参考内核阶段 2.3 的 spawn 模板）。

## 六、约束

### [门禁] 硬约束

- **数量门禁（按原型分设）**：`planner` ≤ 3、`maker` ≤ 1、`reviewer` 维度 ≤ 5；**领域模式下以该领域 `role-registry.md` 的「编排规则」为准**
- **单写门禁**：同一产物只允许一个角色写，禁止多角色共写
- **深度门禁**：角色禁止再 spawn 子 agent（编排深度 1 层，见 `ai-team-tool-global-rule`）
- **能力门禁**：spawn 前确认子代理具备对应权限（写产出物的角色必须有写权限；纯调研可用只读）

### 避险自查（spawn 前逐项确认）

- [ ] 每个角色职责无重叠（两角色不做同一件事）
- [ ] 无遗漏视角（决策/评审类任务应含反对或把关视角）
- [ ] 依赖拓扑清晰（下游角色知道读谁的产出）
- [ ] 歧义已澄清（需求不清先 `ask_followup_question`，不靠猜）
- [ ] 成本可接受（角色数 = 独立 context + token，能少则少）

## 七、反模式（创建角色时须避免）

| 反模式 | 问题 | 正确做法 |
|--------|------|---------|
| 按职位/头衔造角色 | 脱离实际问题，堆砌身份 | 从子目标所需视角反推角色 |
| 预设角色数超过需要 | 角色冗余，成本失控 | 满足三信号才拆，能合并就合并 |
| 角色职责重叠 | 两角色产出互相踩脚 | 单写多读，边界清晰 |
| 运动员兼裁判 | 同一角色产出又评审自己 | 产生与把关分离为不同角色 |
| 角色越权代劳 | 下游角色替上游做决策 | 只做本职，歧义向上反馈 |

## 八、示例（仅供参考，非模板）

以下示例展示「问题 → 推导出的角色」，用于体会推导思路；实际角色始终由当前问题的子目标决定，不照搬。

- **调研类问题**（摸清某领域现状）→ 拆出「调研者（收集素材）」+「分析者（下结论）」，若需多方观点再加「质疑者」制衡。
- **产出类问题**（写一份方案）→ 拆出「起草者（产出成稿）」+「评审者（挑问题把关）」。
- **决策类问题**（要不要做某件事）→ 拆出「主张者（论证可行性）」+「反对者（专挑漏洞）」+「综合者（收敛结论）」。
- **组织类问题**（涉及多方立场）→ 按实际涉及的立场/职能拆角色，让不同立场各自独立表达，再综合。

> 这些例子的价值在于展示「视角驱动」的推导，而非提供可复用的角色名单。
