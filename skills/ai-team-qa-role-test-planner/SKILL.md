# 测试领域 — 计划者扩展（`qa` · 原型 planner · 变体 test-planner）

## 触发

领域=qa 且变体=test-planner 时经「第零步：领域适配」启用。**不单独 spawn**，仅补全/覆盖基座中标 `[领域扩展]` 的步骤。

## 覆盖范围

| 基座位置（`ai-team-role-planner`） | 本扩展的作用 |
|-----------------------------------|-------------|
| 第一步 需求收集 · 字段 7（领域专属字段） | 提供测试专属字段与取值（见 §一） |
| 第一步 意图澄清 · 穷举确认 | 追加「用例接入与解析」「环境依赖聚合」（见 §二 / §三） |
| 第二步 角色清单适配检查 | **覆盖视角推导**为按注册表取固定清单（见 §四） |
| 第三步 产出蓝图文档 | **覆盖产出路径**为 `test-plan.md` + 追加测试专属章节（见 §五） |
| 第四步 置信度评估 | 追加测试专属检查项（见 §六） |

## 一、字段取值

| 字段 | 取值 |
|------|------|
| 目标平台 | `harmony`（鸿蒙）/ 其它。**关键字段**，下游据此加载平台特化 skill |
| 测试类型 | 功能验证 / 回归验证 / 冒烟 / 验收 |
| 被测应用 | `bundleName`（**由用户提供，禁止按关键词猜**）+ 被测版本（HAP 路径 或 设备已装版本） |
| 用例来源 | 用例文档（Excel / CSV / Markdown / 文本）/ 用户口述目标 / 无（需现场设计） |
| 执行设备 | 已连接设备 serial（多设备时必填）/ 模拟器 / 未就绪 |
| 期望产出 | 测试报告 / 缺陷单 / 仅执行结论 |

### 平台识别（[门禁] 判不出就问用户，不猜）

从用户需求关键词判定 `目标平台`：

| 关键词 / 特征 | 判定 |
|---------------|------|
| 鸿蒙 / HarmonyOS / ArkUI / ArkTS / `.ets` / `.hap` / `devecocli` / `hdc` / 真机 | `harmony` |
| 其它平台标识 / 无法判断 | **非鸿蒙** → 按 `platform-map.md`「未命中平台」处置（给选项告知用户当前无对应执行侧 skill） |

> **本领域当前只有 `harmony` 执行侧**：判定为非鸿蒙时**不得默认套用鸿蒙流程**，也不得假装支持；必须在 `test-plan.md` 中写明平台结论与用户选择。

> **测试专属字段的作用**：`bundleName` 与「被测版本」是**结论有效性**的前提（测的是哪个包）；「用例来源」决定是否产出 `test-cases.md`；「执行设备」决定后续命令是否需 `--device <serial>`。

## 二、用例接入与解析（[门禁] 按工具流程执行）

### [门禁] 已有现成计划时不重复解析

编排方在运行模式弹窗中提示「检测到既有计划：{路径}」时，**先确认复用意图**，不得直接重新解析：

| 情况 | 动作 |
|------|------|
| **沿用既有计划** | 读既有 `test-plan.md` / `test-cases.md` → 与用户确认「沿用 / 调整范围 / 重新解析」→ 补充本轮的**结论有效性前提**（被测版本 / 设备 / 环境依赖）→ 产出更新后的 `test-plan.md`（`版本 +1`） |
| **重新解析** | 走下方流程（原计划标注为被取代） |
| 用户未表态 | `ask_followup_question` 给选项问清，**不默认重新解析**（重复解析会重刷用例编号、打断历史结论的追溯） |

### 用户提供用例文档或口述清单时

1. `use_skill ai-team-qa-tool-testcase-plan`
2. 按其 **§一 解析用例原文档** 执行（**不得要求用户改格式**，字段按语义映射）
3. 按其 **§一 1.2 回读校验** 向用户确认三项：**用例总条数 / 缺字段条数 / 归并条数**
4. 产出 `{artifact_dir}/test-cases.md` 与 `{artifact_dir}/test-plan.md`

> **[门禁] 只做结构归一，不改用例语义**：**不得修改预期结果、不得新增或删除用例**；发现原文矛盾 / 重复 / 歧义 → 集中列「待澄清清单」，**一次** `ask_followup_question` 问清，不自行裁决。
> **无用例文档时**：与用户**一次问清**「待验证链路 + 每条判定方式」，按工具流程现场整理成临时用例序列表，**不跳过判定方式直接开跑**。

## 三、环境依赖聚合（[门禁] 一次问清，不逐条打扰）

按 `ai-team-qa-tool-testcase-plan` **§3.3 环境依赖聚合** 产出「需用户物理操作」清单（操作 / 涉及用例 / 副作用 / 生效校验方式 / 恢复方式 / 降级），并覆盖其**固定必列项**：

| 类别 | 本领域要点 |
|------|-----------|
| 应用定位 | `bundleName` 由用户提供；**不得按中文名拼音臆测** |
| 登录态 / 账号 | 是否已登录、账号等级、剩余权益次数 |
| **破坏性数据操作** | 逐项列出让用户勾选（置顶 / 移动 / 删除 / 重命名 / 新建 / 上传…）；**未勾选记未覆盖** |
| 不可逆权益消耗 | 单独确认（扣减次数、切换后不可回退） |
| 第三方应用依赖 | 设备是否已装并登录（如微信） |
| 服务端数据 / 配置 | 目标数据是否具备（不具备 → 记未覆盖，不得伪造通过） |
| 网络状态 | 是否需断网 / 弱网类（**执行序放最后**） |
| 设备就绪 | 设备已连接 / 未授权 / 锁屏 / 应用未安装（见 `ai-team-qa-tool-workflow` §二） |

> **合并进「计划确认」那一次询问**，不另起一轮。协同判据与选项规范见 `ai-team-qa-tool-workflow` §二。

## 四、角色清单（覆盖基座视角推导）

**[门禁] 本领域角色固定为 `test-planner` → `runner`，你自身不参与「是否需要计划者」的决策**（你是固定前置角色，见 `ai-team-qa/SKILL.md`「角色清单」表）。故基座第二步在本领域**只保留「是否需追加角色」的判断**：

| 情况 | 动作 |
|------|------|
| 默认（绝大多数） | 清单固定 `test-planner + runner`，**不打扰用户** |
| 用户主动要求独立复跑复核 | 建议追加一个 `maker·runner`（用户确认后写入 `test-plan.md` 与完成信号，PM 标注「用户指定」） |

> **[门禁] 变体只可从注册表取**，不得自行发明变体名；本领域**不设 reviewer 维度**，不得建议新增审查角色（理由见注册表 §二）。

## 五、产出蓝图文档（覆盖产出路径）

> 产出前显式加载 `use_skill ai-team-tool-report`（统一元信息模板 + 写入路径），**仅本步骤加载**。

**覆盖**基座的 `{artifact_dir}/designer-report.md` → 本领域产出 **`{artifact_dir}/test-plan.md`**（结构由 `ai-team-qa-tool-testcase-plan` §三 定义），并在其中追加测试专属章节：

```markdown
## 测试范围与依据
- 依据文档：{用例来源文件 / 需求章节}
- 覆盖范围：{模块 / 链路}
- 明确不测：{排除项及原因}

## 结论有效性前提
- 被测应用：{bundleName}
- 被测版本：{HAP 路径 + 构建时间} 或 {设备已装 versionName（新鲜度未校验）}
- 执行设备：{serial / 模拟器}

## 环境依赖与用户操作清单
（按 §三 聚合，含破坏性操作待勾选清单与登录态确认项）

## 用时粗估
{用例条数 × 单条平均耗时 + 跨用例导航与取证开销}（无实测样本时标明「粗估」）
```

- 无用例文档时不产出 `test-cases.md`，`test-plan.md` 内嵌临时用例序列表
- **计划必须经用户确认**（门禁出处：`ai-team-qa-tool-testcase-plan` §四），未确认不得进入执行

## 六、置信度追加检查项

在基座检查清单之外追加（每项 10 分，计入清单总分）：

| # | 检查项 | 得分 |
|---|--------|------|
| +1 | 目标平台已识别（非鸿蒙时已按 `platform-map.md` 未命中处置告知用户） | 0 / 10 |
| +2 | `bundleName` 与被测版本已确认（非臆测） | 0 / 10 |
| +3 | 计划已获用户明确确认（非「随便/都行」） | 0 / 10 |

> 追加后清单满分相应上调，主观补充仍为 40 分；阈值不变（≥ 85% 放行）。
