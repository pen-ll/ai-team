# ai-team 通用多 Agent 协同内核 — 设计文档

> 最后更新：2026-09-09 | 状态：通用编排内核总入口

## 一、定位与分层

`ai-team` 是**领域无关的通用多 Agent 协同编排内核**，作为总入口面向任意复杂难题（写作、策划、调研、决策分析、方案评审等）。

它与 `ai-team-dev`（软件开发领域插件）的分层关系：

```
ai-team（通用编排内核 / 总 PM）
   │  领域识别 → domain-map.md 路由
   ├─ development → ai-team-dev（软件开发领域 PM，完整接管）
   ├─ generic     → 内核内置动态角色编排
   └─ 未来领域    → 挂载新领域 PM（ai-team-dom-{领域}）
```

**核心思想**：任何复杂问题都可用「PM 主会话协调 + 多角色分工协作」求解。`ai-team-dev` 作为「软件开发领域」插件挂载于本内核之下。

## 二、设计动机

| 问题 | 本内核的解法 |
|------|-------------|
| 通用场景无统一角色范式，固定角色无法覆盖任意领域 | 动态角色编排：现场拆解任务、即时定义角色 |
| 开发专属逻辑（复杂度路由、平台适配）不应污染通用编排 | 领域路由：开发场景委托 `ai-team-dev`，内核保持领域无关 |
| 编排机制（team_create + spawn + send_message + 置信度门禁 + 回收）天然适用于任意复杂问题 | 抽象为统一内核，领域通过注册表按需挂载 |

## 三、核心机制

### 1. 领域路由

`domain-map.md` 注册表驱动。命中已注册领域 → 委托对应领域 PM；未命中 → 动态编排。新增领域只需在注册表加一行。

### 2. 动态角色编排

不预设角色（designer 为唯一预设前置角色，是否启用由 1.0 Q1 选择）。进入动态编排后，PM 按以下顺序推进：

1. **阶段 0.2 任务标识**：产出目录隔离为 `docs/ai-team/{任务标识}/`
2. **阶段 1.0-A 预估角色推导**：PM 用 `ai-team-tool-role-composer` 仅凭用户原始问题推导候选清单（仅用于填弹窗选项；不落盘、不传递、不作为权威拆解）
3. **阶段 1.0 编排方案确认**：一次 `ask_followup_question` 多问同出——Q1 角色配置（{单角色 | 标准} × {含需求人员 | 不含需求人员} 四选一，选项文字带预估角色名）/ Q2 流程运行模式
4. **阶段 1.2 团队调整机制**：designer 深挖需求后检查初始规模是否仍合适，不合适则**直接向用户建议增删角色类型**，用户确认后写入完成信号；PM 以「最终清单」为准 spawn（**最终清单覆盖初始选择**）
5. 用户选「不含需求人员」时（1.0 Q1 的 `单角色·不含` / `标准·不含`），1.0-A 的预估清单即最终清单

PM **不自行拆解任务、不读角色报告全文**。子目标所需视角反推角色组合（四要素：角色名/职责/产出物/验收标准）。这解决了「开发四角色」无法覆盖任意领域的问题。

> **规模判据**：单角色/标准按**执行视角种类数**分界——全部为同类执行视角 → 单角色；出现把关/质疑/调研等不同视角 → 标准。需求人员**不计入规模判定**，由 1.0 Q1 选项的「含 / 不含」决定。

### 2-A. 角色规模与团队调整

| 概念 | 说明 |
|------|------|
| 初始规模 | 用户在 1.0 弹窗 Q1 中选择（{单角色 \| 标准} × {含 \| 不含需求人员}） |
| 最终清单 | designer 深挖需求后确认的清单，**覆盖初始规模**；由完成信号的 `最终清单` 字段传给 PM |
| 角色实例数 | 同视角的多个角色（由体量/上下文隔离决定），不计入「视角种类数」 |

> designer 只做"建议 + 与用户确认"，**spawn 权始终在 PM**；调整后仍须满足 2-5 角色数量门禁。

### 2-B. 流程运行模式（全自动 / 手动确认）

有上下游角色依赖的流程（designer → 多交付角色串行接力）中，spawn 任何角色前由 PM 用 `ask_followup_question` 询问用户运行模式（已并入 1.0 的同一次多问弹窗），并随 spawn prompt 传给每个角色：

| 模式 | 完成信号流程 |
|------|-------------|
| **全自动** | 角色完成 → `send_message` 通知 PM → PM 直接放行下一角色（默认） |
| **手动确认** | 角色完成 → `ask_followup_question` 向用户确认完成度 → 用户确认 → 才 `send_message` 通知 PM → PM 放行下一角色 |

> 手动确认的完成度确认发生在角色会话内，PM 收到完成信号后不重复向用户确认。角色完成通知行为由各角色 skill 的「通知 PM」步骤内「完成通知模式」门禁约束。

### 3. 复用策略

| 资产 | 复用方式 |
|------|----------|
| `ai-team-dev` 整套 | 作为开发领域插件，通过注册表 `use_skill ai-team-dev` 委托 |
| `ai-team-tool-global-rule` | 通用约束（身份/先思考/歧义/异常/选项按钮），所有动态角色继承 |
| `ai-team-tool-auto-tune` | 自我优化，收尾静默收集建议 |
| `ai-team-tool-report` | 产出物格式思想（结构化表格、统一元信息） |
| `ai-team-tool-web-read` | 网页输入读取，调研类任务可用 |

> `minimal-code` / `security` / `ui-ux` / `debug-loop` 属开发领域，保留在 `ai-team-dev` 内，不通用化。

### 4. 通用置信度门禁

检查清单（60 分：目标达成度 / 产出完整性 / 结构清晰 / 边界处理 / 验证通过 / 报告完整）+ 主观补充（40 分），≥85% 放行 / 70%-84% 迭代 / <70% 请求用户介入。与 `ai-team-dev` 体系一致。

### 5. 产出物隔离

`docs/ai-team/` 与 `docs/ai-team-dev/` 分离，避免领域间文件污染。

## 四、触发协调

| 入口 | 聚焦关键词 |
|------|-----------|
| `ai-team` | 复杂问题、多角色、多专家、一起解决、帮我分析/策划/调研/评审 |
| `ai-team-dev` | 编码、开发、功能、模块、bug、崩溃、报错、重构 |

> `ai-team` 是**总入口**：所有任务先经内核判定领域，命中 `development` 时由内核 `use_skill ai-team-dev` 委托给开发领域 PM，由后者完整接管。

## 五、领域扩展指南

新增一个领域（如「数据分析」「写作」）：

1. 编写领域 PM skill（可复用 `ai-team` 的编排模式，也可复用 `ai-team-role-*` 通用角色）
2. 在 `domain-map.md` 注册表加一行：`| {标识} | {名称} | use_skill {PM名} | {触发特征} |`
3. 内核零改动，自动生效

## 六、推荐模型

多 Agent 协同需 PM 主会话 spawn 角色 Agent，对模型能力有下限要求：

| 维度 | 最低要求 | 参考数值（DeepSeek-V4.1-Flash） |
|------|----------|--------------------------------|
| 模型评分 | ≥ DeepSeek-V4.1-Flash | MMLU-Pro 74.1（Base）· DeepSWE v1.1 74.2 · Terminal-Bench 2.1 90.6 |
| 上下文窗口 | ≥ DeepSeek-V4.1-Flash 同档 | 1M token（100 万 token）；最大输出 384K |

> 参考数值取自 DeepSeek-V4.1-Flash 公开技术报告（2026-09-10 发布，MIT 许可；总参数 552B / prefill 8B · decode 16B 激活，原生 1M token 上下文），实际以官方为准。
>
> 实测 `hy3` 模型流程不通畅：PM 未正常 spawn 角色 Agent，任务直接在 PM 主会话内执行。低于 `DeepSeek-V4.1-Flash` 评分/上下文的模型不建议使用本内核。
> 目前已实测可用模型：DeepSeek-V4.1-Flash（推荐）、DeepSeek-V4-Flash、DeepSeek-V4-Pro、GLM5.2-5.3、Kimi-K3
