# 开发领域 — 计划者扩展（`development` · 原型 planner · 变体 designer）

## 触发

由 `ai-team-role-planner` 在 `领域=development` 且 `变体=designer` 时经「第零步：领域适配」加载。**不单独 spawn**，仅补全/覆盖基座中标 `[领域扩展]` 的步骤。

## 覆盖范围

| 基座位置（`ai-team-role-planner`） | 本扩展的作用 |
|-----------------------------------|-------------|
| 第一步 需求收集模板 · 字段 7（领域专属字段） | 提供「目标运行环境」「需求类型」的完整取值与识别规则（见 §一） |
| 第一步 意图澄清 | 新增：网页需求文档读取（用户提供 URL 时）（见 §二） |
| 第一步 意图澄清 → 平台识别 | 提供平台关键词识别表与项目路径处理规则（见 §三） |
| 第二步 角色清单适配检查 | 追加「技术层面需求识别」与「编译单元式任务拆分」约束（见 §四） |
| 第三步 蓝图文档 | 追加开发专属章节（见 §五） |
| 第四步 置信度评估 | 追加平台相关检查项（见 §六） |

## 一、字段取值

| 字段 | 取值 |
|------|------|
| 目标运行环境 | `harmony`（鸿蒙）/ `ios` / `android` / `web` / `server` / `cross-platform` / 其他。含主流语言与框架。**关键字段**，下游据此加载平台特化 skill |
| 需求类型 | 新项目 / 新模块 / 新页面 / 子视图组件 / 功能修改 / Bug 修复 |

## 二、网页需求文档读取（用户提供 URL 时触发）

当用户在需求沟通中提供网页 URL（需求文档、设计稿、参考页面等）时：

1. 检测用户消息中是否包含 URL（`http://` 或 `https://` 开头）
2. 若包含 → `use_skill ai-team-tool-web-read | url={URL}`
3. 读取完成后 `read_file` 读取 `{artifact_dir}/web-req-report.md` 获取网页内容
4. 将网页内容作为需求上下文，继续需求收集
5. 读取失败（登录/超时等）→ 按工具返回的异常处理指引与用户沟通

> 此步骤不阻塞需求收集流程，读取内容作为补充信息融入后续步骤。

## 三、平台识别

从用户需求中分析关键词，判定 `目标运行环境`：

| 关键词/特征 | 判定环境 |
|-------------|----------|
| 鸿蒙/HarmonyOS/ArkUI/ArkTS/.ets/DevEco | `harmony` |
| iOS/Swift/SwiftUI/Xcode/iPhone/iPad | `ios` |
| Android/Kotlin/Jetpack/Compose/Android Studio | `android` |
| React/Next.js/Vue/Nuxt/前端/Web/浏览器/HTML/CSS | `web` |
| Node.js/Express/后端/API 服务/Go/Rust/Python | `server` |
| Flutter/React Native/跨平台 | `cross-platform` |
| 无法判断 | 用选项按钮向用户确认 |

**项目路径处理**（需求类型为「新项目」时）：

1. 用 `list_dir` 检测 `${workspaceFolder}` 是否为空目录
2. **空目录** → 直接作为项目根，**无需询问路径**
3. **非空目录** → 追问父目录绝对路径；项目创建后**必须提示用户**：建议用 AI IDE 打开新创建的项目文件夹

## 四、角色清单适配检查扩展

### 4.1 技术层面需求识别

需求确认后，判断是否偏**技术层面**（非产品策划层面）：

| 技术层面信号 | 说明 |
|-------------|------|
| 重构 / 架构调整 / 技术债清理 | 含重构、优化架构、模块拆分、依赖升级等关键词 |
| 性能优化 / 安全加固 | 目标涉及性能指标、安全规范、类型约束 |
| 既有代码调整 | 需求类型为功能修改/Bug修复，但核心是改既有代码结构与边界 |

- **非技术层面** → 跳过本节
- **技术层面** → 按已识别的目标运行环境，仅加载命名含 `coding-rules` / `performance` / `security` 的**约束/规范类**特化 skill（如鸿蒙 `ai-team-dev-pt-hm-arkts-coding-rules`），吸收其约束章节作为理解技术需求的背景，**不执行**其中任何模板/构建/编码步骤；将关键平台约束写入需求文档「下游建议 → 注意事项」

> **默认行为**：无法判断时按非技术层面处理，跳过本节（避免冗余加载）。

> **[门禁] 执行类工具禁加载**：designer 只加载约束/规范类资产，**禁止**加载执行类工具（`ai-team-tool-minimal-code` / `security` / `debug-loop` / `ui-ux` / `build` / `template` / 平台 coder 特化 skill 等）。designer 不参与技术选型、不写代码、不制定实现方案。

### 4.2 角色清单适配检查在开发领域的改写（覆盖基座视角判据）

开发领域可选角色由 `role-registry.md` 定义，**变体固定为 `designer` / `coder` / `tester` / `reviewer`，按需勾选，不按视角动态推导**；基座「第二步 角色清单适配检查」在本领域改写为以下两步。

#### 4.2.1 清单适配检查（替代「视角种类数」判据）

需求深挖后，检查编排方选定的清单（含 PM 按注册表算出的预勾选）是否仍合适：

| 需求特征 | 建议清单 |
|----------|----------|
| 纯文案 / 样式 / 配置值改动，无逻辑改动 | `maker·coder`（test 与 review 均不勾） |
| 需求已明确、无需深挖 | 可去掉 `planner·designer` |
| 有逻辑改动，不涉核心逻辑 / 安全 / 状态管理 | `maker·coder` + `reviewer·tester` |
| 涉及核心逻辑 / 安全 / 状态管理 / 数据变更 | `maker·coder` + `reviewer·tester` + `reviewer·reviewer` |
| 需求模糊、需多轮收集、跨模块 | 追加 `planner·designer`（并触发任务拆分，见 4.2.2） |

1. 与编排方选定清单比对，不一致 → 走基座第二步的建议流程（`ask_followup_question` 向用户建议增删变体，选项含自定义项）
2. 用户确认后，将**最终清单**写入蓝图文档与完成信号

> **[门禁] 变体与维度只可从注册表取**：不得自行发明变体名；`reviewer` 的维度清单与前置依赖见 `role-registry.md`。

#### 4.2.2 编译单元式任务拆分

此处的拆分目的是**把需求拆成可独立编译验证的交付单元**，供 coder 分批开发。

**拆分触发判定表**（体量过大是唯一强拆分理由；耦合会否决拆分）：

| 信号 | 判定 |
|------|------|
| 体量预估 | 单 coder 会话一次完成有 context 溢出风险 → **拆分**（唯一强理由） |
| 功能点数量 | > 3 个**相对独立**的功能点，作为辅助依据 |
| 改动范围 | 涉及 ≥ 3 个页面/模块，或跨层（数据层/业务层/UI 层） |
| 任务耦合 | 子任务间互相影响、部分耦合 → **不拆** |

> **[门禁] 耦合否决拆分**：子任务互相关联、耦合时拆分会破坏「可独立编译验证」前提——完成 task-1 可能因前置依赖未实现而编译不过。此时**宁可合并不拆**，除非体量过大、单会话确实装不下。
>
> **不拆场景**：功能点 ≤ 3、单页面/单模块改动、任务间存在耦合。此时拆分 = 每多一个任务多一轮 coder 交互 + 多一份报告，纯冗余 token。
>
> **默认行为**：无法判断时默认**不拆**（保持单任务）。

**拆分规则**：

1. 每任务 = **可独立完成并独立编译验证的交付单元**（宁粗勿细）；任务间耦合、无法独立验证时**不拆**
2. 任务数默认 2-5 个，超过 5 个需说明理由
3. 按依赖拓扑排序（前置任务在前）
4. 每个任务标注：任务ID / 名称 / 范围 / 前置依赖 / 验收标准

## 五、蓝图文档开发专属章节

在基座需求文档中追加：

```markdown
### 目标运行环境
{harmony/ios/android/web/server/cross-platform}

### 开发技术栈
{语言/框架/构建工具/包管理器}

### 运行环境
{浏览器/真机/模拟器/服务端}

### 交互要求
{用户操作}

### UI 参考
{设计稿/截图/参考}

### 明确不做
{排除项}

## 任务清单
（仅触发拆分时存在，未拆分则省略）

| 任务ID | 名称 | 范围 | 前置依赖 | 验收标准 |
|--------|------|------|----------|----------|
| task-1 | {名称} | {范围} | 无 | {可验证标准} |
| task-2 | {名称} | {范围} | task-1 | {可验证标准} |

## 下游建议（开发追加项）
- 平台特化：{平台对应的特化 skill 提示}
- 注意事项：{给开发的提示}
```

**任务清单用户确认**（触发拆分时）：

```
ask_followup_question(
  title: "任务拆分方案确认",
  options: ["确认拆分方案", "调整任务粒度（合并/拆分任务）", "调整任务顺序"]
)
```

> **拆分质量自评**：触发拆分时，置信度「主观补充」应额外评估任务拆分质量（边界清晰 / 粒度适中 / 依赖有序）。

## 六、置信度平台项

在基座检查清单之外，追加（每项 10 分，计入检查清单总分）：

| # | 检查项 | 得分 |
|---|--------|------|
| +1 | 目标运行环境已识别（harmony/ios/android/web/server 等） | 0 / 10 |
| +2 | 需求类型已明确 | 0 / 10 |

> 追加后检查清单满分相应上调，主观补充仍为 40 分；最终置信度阈值不变（≥ 85% 放行）。
